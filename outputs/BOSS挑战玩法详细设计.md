# BOSS挑战玩法详细设计

## 一、目标与设计原则

本玩法为玩家提供可重复参与、难度分层、可独立结算的团队首领挑战。首领战斗复用 `src/server/scripts/Custom/WorldBoss` 中已经实现的 BOSS AI、技能和召唤物逻辑，不重新复制一套首领战斗脚本；挑战系统只负责入口、队伍校验、挑战状态、场地边界、难度参数、胜负结算和奖励。

设计目标：

- 10人团队为基础战斗规模，支持单人或小队参与时按实际人数缩放；也可先限定为固定人数，避免首期平衡范围过大。
- 同一首领提供多个挑战难度，难度影响生命值、伤害、技能节奏、机制组合和奖励，不依赖原版团队副本的普通/英雄进度。
- 玩家可在统一大厅、NPC或挑战界面选择首领、触发方式和难度；挑战结束后有清晰的胜利、失败、重试和离场流程。
- 挑战区域在战斗期间只服务于当前挑战团队，不允许其他团队介入或蹭奖励。
- 可重复挑战，但通过词缀、轮换目标、限时目标、团队纪录、阶段性奖励等制造变化，避免只靠重复堆数值。

## 二、地图与实例边界（必须先定案）

### 2.1 格鲁尔巢穴地图的实际约束

格鲁尔巢穴地图 ID 为 `565`，其地图类型是可实例化团队副本。对该地图执行普通传送并不会得到一个供所有玩家共用的公共地图；核心会按玩家/队伍的副本难度、保存和绑定状态选择或创建实例。因此，“使用格鲁尔巢穴区域”“不与原版70级团本进度冲突”“挑战区域彼此隔离”不能通过单纯传送坐标实现。

建议将需求中的“不使用这个副本实例”具体解释为：**不进入或改写原版格鲁尔巢穴遭遇流程、不共享原版副本进度/首领击杀状态、不要求玩家拥有格鲁尔巢穴进度**。挑战系统可以继续使用地图 565 的场景资源，但使用自己管理的挑战实例和遭遇状态。

### 2.2 推荐方案：独立挑战实例，复用地图场景

- 地图仍使用 565 的场景、地形与坐标，但挑战进入流程由独立的挑战入口控制。
- 使用挑战专属的实例状态管理；不得调用原版格鲁尔首领的遭遇状态、门控进度和击杀保存逻辑。
- 挑战难度、挑战 ID、队伍归属、奖励资格均由挑战系统管理，不以原版副本难度或副本首领击杀记录作为条件。
- 同一地图可并发创建多个挑战实例，每个实例只属于一个挑战团队；玩家现有的原版格鲁尔绑定不得阻止挑战入场，是否能实现需要在目标核心版本上验证实例创建/匹配入口的扩展方式。
- 首期应建立专用挑战 InstanceScript/入口路由，不要直接给原版 `instance_gruuls_lair` 增加玩法状态，防止原版副本行为互相污染。

这仍然是“实例”，但不是“原版格鲁尔副本进度实例”。这是满足多人挑战隔离、封场、并发和安全结算的推荐解释。

### 2.3 严格非实例方案：不能满足完整隔离

如果“不使用副本实例”是指连挑战专属实例也禁止，那么同一块 565 地图无法自然提供多个互不干扰的团队空间。此时只能选择：

1. 改用非实例化地图上的专用场地，并由脚本维护挑战团队名单、边界和结算；或
2. 让所有挑战团队共用同一个公开场地，设置全局单场预约/排队锁，上一场结束后下一队才能进入。

这两种方案都不具备每队独立副本的隔离能力。非实例世界场地还要额外处理其他玩家可见、跨团队仇恨、死亡跑尸、传送绕过封锁和服务器重启恢复等问题，不推荐用于多人正式挑战。

### 2.4 区域封闭与参与者生命周期

封闭不是只关一扇门。建议挑战状态为：`等待组队`、`准备中`、`战斗中`、`胜利结算`、`失败结算`、`清理中`。

- 准备中：检查队长、人数、等级、队伍成员在线状态、挑战资格和入场消耗；确认后将所有成员传入同一挑战实例。
- 开战时：冻结本场参与者名单和奖励资格，记录玩家 GUID 与挑战 ID。开战后不允许新玩家加入；掉线玩家在短暂重连窗口内回到原挑战。
- 战斗中：入口关闭或禁止非本场玩家进入；挑战成员离开战斗区域时按规则警告、短暂宽限并传回场地，避免单次误操作导致惩罚。不可只依赖碰撞门。
- 死亡：由规则决定允许战斗复活、战斗内复活次数或死亡后只能观战；释放灵魂后不应进入原版格鲁尔墓地流程。失败/团灭时统一结束挑战并清理首领及召唤物。
- 胜利/失败：锁定结算，发放一次奖励，清理临时生物与场地状态，送回大厅或保留短暂领奖时间后离场。
- 断线/服务器重启：明确挑战是否暂停。推荐挑战实例短期保留，记录挑战状态和参与者；无法恢复时安全判负或取消，并按规则返还入场消耗，不能产生重复奖励。
- GM、传送、传送门和跨地图技能：设计时检查所有绕过正常入口/出口的路径；至少确保不能加入他队挑战或重复领取奖励。

## 三、首领复用与难度模型

### 3.1 复用现有世界BOSS

现有 `WorldBoss` 目录提供 `WorldBossGuardAI`、`WorldBossSummonAI`、BOSS 战斗脚本及相关数据库内容。挑战系统应以已有 BOSS entry/AI 为基础生成挑战首领，尽量复用技能、召唤物和伤害缩放逻辑。

需在开发前逐个核对目标首领的 AI 是否依赖世界地图假设，特别是：

- `WorldBossGuardAI` 的队伍归属锁定与敌对反应守卫是否适用于挑战团队和实例地图。
- `CheckLeash()` 与副本内脱战、挑战场地边界、回家点处理是否冲突。
- 世界首领的固定缩放表是否适合挑战难度；避免挑战难度倍率和世界首领倍率重复相乘。
- 召唤物清理、危险区域、阶段重置、首领死亡回调是否能由挑战状态系统可靠获知。
- 阵营/反应全局 Hook 是否会错误地影响同一首领在原世界刷新时的行为。

若必须修改公共 `WorldBossGuardAI`，应增加明确的挑战上下文或可配置策略，保证原世界刷新行为保持不变；不建议为了挑战直接将所有世界首领逻辑改成副本逻辑。

### 3.2 难度阶梯

建议首发采用四档，名称与实际倍率可在测试后定稿：

| 难度 | 定位 | 首领强度与机制 | 奖励方向 |
|---|---|---|---|
| 练习 | 熟悉技能、低门槛体验 | 基础生命/伤害，宽松狂暴时间；关键技能有明显提示 | 基础挑战货币、低概率外观材料 |
| 普通 | 标准10人体验 | 作为数值平衡基准，完整核心技能循环 | 稳定基础奖励、周常进度 |
| 英雄 | 熟练团队挑战 | 提高生命/伤害，加入或强化一项机制，缩短安全窗口 | 更高货币、装备/外观进阶材料 |
| 传奇 | 高水平挑战 | 完整机制组合、严格狂暴与失误惩罚，适合冲榜 | 首通/赛季奖励、外观和称号，不以无限属性碾压奖励 |

具体倍率不在方案阶段写死。建议先通过 10 人标准队伍实测，再分别调整生命、伤害、狂暴时间和机制，不用单一的全局倍率同时放大所有内容。首领的等级和原版 10 人/25 人难度识别也不应被误认为挑战档位；挑战档位由挑战系统明确传给首领 AI。

### 3.3 人数缩放

优先选定一种规则，不要在首期同时支持固定人数、自由人数和 NPCBot 混编的复杂组合：

- 推荐首期限定 10 人团队，玩法验证和数值调优最清晰。
- 若需要支持 1–10 人，以开战时的有效玩家人数为基础缩放首领生命与部分伤害；技能机制仍以团队职责完整为前提，不能简单按人数缩放所有技能。
- NPCBot 是否计入人数与是否获得奖励应分开定义；建议 NPCBot 可参与战斗但不占玩家奖励资格，且由团队配置决定是否开启。
- 开战后人数变化不重新计算本场难度，避免玩家中途进出操纵数值。

## 四、五种玩家触发玩法

五种方式共享同一挑战状态、队伍校验、实例隔离和结算系统，只改变玩家如何获得挑战机会或启动挑战。可同时上线其中数种；每种必须明确个人/团队资格、每日/每周限制、奖励能否叠加及匹配失败补偿。

### 方案一：挑战大厅自由选王（稳定常驻）

**体验定位：** 简单直接、适合学习机制和固定团队反复练习。

**触发流程：** 玩家在大厅与挑战官对话，依次选择首领、难度、队伍人数规则；系统显示推荐人数、预计时长、关键机制和入场消耗。队长确认后全队校验并传入挑战实例，短暂准备倒计时后生成首领。

**变化设计：** 每周轮换一个“推荐首领”和一个额外挑战目标，例如限时击杀、全员存活或不触发某种机制；其他首领仍可自由挑战。每日首次完成推荐目标给额外货币，重复挑战仍可练习但奖励递减或仅给基础收益。

**优点：** 入口可预测、方便调试与教学；玩家能主动选择团队能力范围。

**风险控制：** 防止低难度刷取高阶货币；同一挑战完成只结算一次；入场消耗在创建实例成功后扣除，创建失败或服务异常取消时返还。

### 方案二：团队挑战令牌（惊喜与收藏驱动）

**体验定位：** 通过掉落、任务或活动获得挑战令牌，带来开箱式惊喜，但不让随机决定是否能玩。

**触发流程：** 玩家获得“挑战密令”，使用时生成密令所指向的首领、难度范围或特殊规则；队长可邀请队伍并预览结果，确认后创建实例。令牌可来自日常任务、挑战周常、活动奖励或大厅兑换。

**随机边界：** 随机内容采用可解释的奖池；玩家在使用前至少知道难度范围和奖励类别。传奇难度不能由低等级玩家意外触发；高难度密令需要全队二次确认。提供稳定兑换渠道，避免连续随机失败带来挫败。

**重复性设计：** 同一密令可有常规版本和变异词缀版本；收集不同首领密令、完成首次击杀和全词缀图鉴给予收藏型目标。重复获得已有密令可分解为兑换材料。

**优点：** 每次开战略有不同，适合作为惊喜玩法和活动内容。

**风险控制：** 不将稀有令牌作为唯一挑战入口；不可交易/可交易需按经济设计选择；令牌消耗和挑战创建必须原子化，不能因断线重复使用或复制奖励。

### 方案三：战术词缀抽选（重复但不枯燥）

**体验定位：** 首领不变，战斗变量组合变化，适合团队长期刷同一首领。

**触发流程：** 队长选择首领和难度后，从系统提供的词缀池中抽取或禁用一项；普通档可无词缀，英雄档至少一个，传奇档按规则组合多个。战斗开始前显示完整词缀说明并由团队确认。

**词缀示例方向：** 首领技能间隔缩短、特定技能附带额外目标压力、场地周期性危险区、阶段转换加速、团队治疗/资源压力变化、限时击杀条件。词缀应改变处理方式而非单纯增加首领血量。

**轮换规则：** 每周固定词缀与每日随机词缀并存；团队可用有限的“战术重抽”调整一次，重抽次数由周常奖励提供。词缀按首领兼容性配置，避免出现无法完成的组合。

**奖励：** 词缀层数越高，挑战积分和外观材料越多；榜单按首领、难度、词缀组合分组，避免不同条件的成绩直接比较。

**风险控制：** 每个词缀必须有清楚提示、适配首领名单和可测试规则；不能随机组合互相冲突的机制；失败不消耗额外付费类物品。

### 方案四：大厅事件/地图线索触发（探索与意外感）

**体验定位：** 通过世界事件、NPC 对话、物件线索或区域调查发现挑战，制造“偶然发现”的体验。

**触发流程：** 玩家在大厅或指定非实例地图收集线索/完成短事件，解锁某个首领的挑战入口；组队后由队长选择难度并进入独立挑战实例。事件入口可以限时出现，但基础挑战大厅仍可常驻。

**惊喜设计：** 事件在每日/每周时段轮换，NPC 提示、场景信号或掉落物暗示即将开放的首领；少量隐藏目标需要完成可读的线索链。隐藏内容奖励以称号、外观、收藏记录为主，不独占角色成长必需资源。

**重复性设计：** 同一事件提供多个可选目标，例如快速完成、无成员死亡、特殊物件互动；完成过的线索可通过图鉴追踪，重复参与仍有挑战积分。

**优点：** 把挑战融入服务器世界，增加探索和社区讨论，不只是点 NPC 菜单。

**风险控制：** 事件状态、区域刷新和参与资格要服务器端校验；不得以地图坐标客户端提示作为唯一权限依据；避免限时窗口过短或跨时区不友好；事件地图本身不承载正式首领战斗，战斗仍进入隔离场地。

### 方案五：匹配排队/挑战合约（照顾散人团队）

**体验定位：** 降低必须已有固定十人团的门槛，鼓励玩家临时组队完成挑战。

**触发流程：** 玩家在挑战面板选择首领、难度、角色职责偏好和是否接受词缀，进入队列；系统匹配后由队长或全员确认，检查人数与职业/职责最低配置，再创建独立实例。队伍也可作为预组队提交，系统补齐缺员。

**匹配原则：** 优先按首领熟悉度、装备区间、职责缺口和等待时间匹配；不强制按职业模板锁死队伍。高难度需完成低难度教学目标或明确确认风险。匹配开始前展示队伍构成、首领机制摘要、预计等待和离队惩罚规则。

**重复性设计：** 每日随机首领、每周团队合约、连续完成奖励和个人最佳记录；失败后可快速重排。为了避免低质量重复组队，可记录完成次数和退出行为，但不使用过重的惩罚限制正常离队。

**优点：** 扩大参与面，缓解固定团队凑人压力。

**风险控制：** 匹配成功但有人拒绝时回到队列而非扣除全队资源；开战前退出不记惩罚；开战后异常离队按宽限和重连规则处理；同一玩家不能同时占多个队列或多个挑战实例名额。

## 五、奖励与进度

建议采用“参与奖励 + 首次/周常奖励 + 表现奖励 + 收藏奖励”分层，避免纯粹依靠装备掉落驱动重复刷取。

- 参与奖励：完成或有效参与后获得少量挑战货币；练习难度可给教学/收藏进度，不产出高阶成长材料。
- 首次奖励：每个首领/难度首次击杀给予一次性奖励，奖励状态按角色或账号归属需提前确定。
- 周常奖励：每周精选目标提供额外货币或密令，控制高价值资源的产出速度。
- 表现奖励：限时、全员存活、词缀完成等提供挑战积分、外观材料或榜单记录，不建议让失败即损失大量资源。
- 收藏奖励：首领图鉴、称号、坐骑/幻化等长期目标，适合支撑赛季玩法。
- 防重复结算：奖励必须绑定挑战 ID 和有效参与名单；首领死亡、实例关闭、玩家重连都不能触发二次发奖。

## 六、排行榜与赛季

- 记录首领、挑战难度、词缀组合、有效人数、完成时间、死亡人数、战斗版本和挑战 ID。
- 只比较相同首领、难度、词缀与人数规则的记录；数值更新后可按版本分榜或重置赛季榜。
- 榜单展示团队名称与成员角色名之前，应确认隐私和改名处理方式；数据只用于排行榜，不作为客户端输入信任来源。
- 赛季奖励优先采用称号、外观和纪念物；强力装备不应只授予榜单前列，避免形成明显滚雪球。

## 七、开发拆分建议

### 第一阶段：可玩的最小闭环

1. 决定地图方案：优先采用地图 565 的挑战专属实例，完全不调用原版 Gruul 遭遇进度。
2. 选 1 个已实现、技能和召唤物依赖最清楚的 `WorldBoss` 首领作为试点。
3. 实现 NPC 入口、队伍校验、单一固定难度、挑战实例创建/传送、战斗开始、团灭/胜利清理和一次性奖励。
4. 验证 `WorldBossGuardAI` 在实例中的目标锁定、脱战、伤害缩放及召唤物清理；必要时以挑战上下文适配，不影响世界刷新。
5. 完成至少以下测试：原版格鲁尔副本可正常进入和击杀；已有原版绑定的玩家可按设计进入挑战；两队并发挑战互相不可见/不可攻击；中途掉线重连；团灭重置；死亡释放；GM 传送；奖励不重复。

### 第二阶段：难度和重复玩法

- 增加练习、普通、英雄、传奇档，并进行真实团队数值测试。
- 上线挑战大厅常驻选择与每周推荐目标。
- 增加词缀池、密令或周常事件中的一种，先验证玩法数据和奖励经济。
- 扩展到更多已实现世界首领，每个首领逐个审核技能缩放、召唤物和场地适配。

### 第三阶段：社交与长期运营

- 评估匹配排队与补员体验。
- 增加排行榜、赛季挑战、隐藏事件和收藏图鉴。
- 根据参与率、失败率、完成时间和奖励消耗调整机制，不只按首领击杀率调数值。

## 八、需要在实施前确认的配置项

| 项目 | 建议默认值/决策方向 |
|---|---|
| 地图 | 场景借用地图 565；挑战使用独立挑战实例，不复用原版 Gruul 进度 |
| 首期人数 | 固定10人，验证稳定后再考虑自由人数 |
| 首发难度 | 普通 + 英雄；练习和传奇可在规则成熟后开放 |
| 首发触发方式 | 大厅自由选择 + 每周推荐；之后增加词缀或密令 |
| 入场成本 | 首期不收高价值消耗品；可用游戏内货币/挑战次数控制资源产出 |
| 失败成本 | 不扣除稀有道具；对创建失败、服务器异常和匹配取消提供返还规则 |
| 重连窗口 | 明确时间窗口与玩家回到原挑战实例的方式 |
| 奖励归属 | 明确按角色还是账号记录周常/首通，并基于开战参与名单结算 |
| NPCBot | 首期默认不计入10人玩家奖励资格；是否允许参战单独配置 |
| 榜单 | 按首领、难度、词缀和人数规则分榜，记录服务器脚本版本 |

## 九、结论

推荐采用“复用地图 565 场景 + 挑战专属隔离实例 + 复用 `WorldBoss` 首领 AI + 挑战系统独立管理难度和奖励”的方案。这样能借用格鲁尔巢穴场景而不进入原版70级团本进度，也能可靠实现封场、并发挑战和奖励归属。

若要求严格禁止任何副本实例，则必须放弃地图 565 上的独立团队空间，改用非实例地图或公共场地排队；不能同时承诺每队独立挑战、封闭区域和完全不使用实例。
