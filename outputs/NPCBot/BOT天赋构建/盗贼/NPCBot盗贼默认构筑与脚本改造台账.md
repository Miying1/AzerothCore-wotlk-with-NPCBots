## 0. 结论速览

1. **盗贼三系默认构筑取自 Icy Veins / wowtbc.gg WotLK Classic 官方 PVE 攻略**（经 realnibba.online 逐天赋交叉验证），点数分配为 **刺杀 51/13/7、战斗 20/51/0、敏锐 19/0/52**，均为 71 点（玩家规则）。已通过层级/前置/maxRank/总点数四重校验，可直接写入 `npcbot_default_talent_plan`（表 1）。
2. **盗贼脚本 `bot_rogue_ai.cpp` 是方案所指的「半程先例」**：A 类已收敛为 `RogueTalents[]` 表驱动（39 项），但**仍是 `spec + 等级区间`，且天赋/雕文混表、用 `master->GetLevel()`、未覆盖 B/C 类**。
3. **清点结果**：3 类载体共 **108 项效果**（天赋 77 / 雕文 25 / 非迁移 6），其中 B 类 59 处、A 类 36 处、C 类 7 处、跨载体 6 处。雕文**仅 1 条在 A 类**（背刺雕文），其余 **24 条全部只在 B/C 类**——按「改造 `ApplyClassPassives()`」理解范围会漏掉 **96%** 的雕文效果。
4. **改造优先级**：先统一等级基准（`me->GetLevel()`）→ C 阶段接入天赋 → D 阶段接入雕文，B 类「先删后用」禁止并行。
5. **构筑取官方攻略值，不自行设计**：三系点数分配（51/13/7、20/51/0、19/0/52）与雕文选择均取自 Icy Veins / wowtbc.gg 的 WotLK Classic PVE 攻略，不按"统一模板"套用。**注意敏锐系官方是 19/0/52，战斗系一点不投**——与"每系都 51/20"的直觉不同。
6. **点数为什么按 71 而不是按预算满配**：方案 5.1 的「不设上限」指**声明上限不设**（构筑写 120 点也不报错），**不是「规划时就该按满配写」**。默认构筑是给人看、给玩家对照攻略的**静态数据**，应当表达「这个专精该怎么点」，因此按玩家规则 71 点构建。运行时 `A(等级) = max(0, 等级-9) + 额外点` 只截断不拒绝——若后续有额外天赋点，`A(等级)` 抬高会让序列尾部自动获得更多生效项，**构筑本身无需改动**。
7. **三系已生成 80.wowdb.cc 可视化链接（含雕文）并有通用生成工具**：链接见 3.3 节；工具 `tools/talent_url.py` 支持全部 10 个职业，后续任何职业/专精都能复用同一命令生成链接（编码算法已完整逆向，三系链接均实测往返一致）。

**URL 编码规则**（逆向自站点 `TalentCalc.js`，与 wowhead / evowow 同源）：

| 项 | 规则 |
|---|---|
| 编码表 | `0zMcmVokRsaqbdrfwihuGINALpTjnyxtgevElBCDFHJKOPQSUWXYZ123456789` |
| 树分隔符 | `Z` |
| 职业前缀 | `ENCODING[oldId * 3]`，oldId：德鲁伊0 猎人1 法师2 圣骑士3 牧师4 盗贼5 萨满6 术士7 战士8 死骑9 |
| 树内编码 | 各天赋 rank（含 0）按槽位顺序拼数字串 → 去尾部 `0` → 奇数补 `0` → 每 2 位 `ENCODING[d0*6+d1]` |
| 尾部分隔符 | 若「补齐后位数 i」< 该树槽位数则追加 `Z`；整个 build 末尾去掉尾部 `Z` |
| 雕文段分隔 | `:`（`talent.js` 的 `location.hash.substr(1).split(':')`） |
| URL 形态 | `https://80.wowdb.cc/?talent#<build>[:<glyphs>]` |

> 1. `if i < slot_count` 比较的是**补齐后的数字位数**，不是编码字符数——写成字符数会多输出一个 `Z`。
> 2. **空树也要输出 `Z`**（因 `0 < slot_count`），写成"空串直接 return"会让后续树错位。
>
> **另一个非代码坑**：通过 URL hash 打开页面后**不能立即读取数据**——`tc_readPound` 是 1 秒轮询，页面 JS 初始化未完成时读到的是中间态（曾误判战斗系 43 点、敏锐系 0 点）。人工核对请等页面标题出现正确点数，或直接用 `setWhBuild()` 验证编码本身。

### 4.1 与方案结论对齐的三处关键问题

1. **`uint8 level = master->GetLevel();`（`:2383`）** → 须改 `me->GetLevel()`（方案原则二）。

## 6. 改造步骤（阶段 B → C → D，盗贼先行）

> 每步都对应方案 2.4 / 7 的规定，逐项迁移、B/C 类先删后用。

### 6.1 阶段 B：等级基准统一（独立提交）

1. `bot_rogue_ai.cpp:2383` `uint8 level = master->GetLevel();` → `me->GetLevel()`。
2. 全文件检索 `master->GetLevel()` 残留（预期仅 `:2383` 一处）。
3. 回归：自由盗贼 Bot 与带 rank 加成的雇佣 Bot，被动获取等级前后对比。

### 6.2 阶段 C：接入天赋分配

1. 引入构筑查询接口（方案 6.4 的 `HasBotTalentRank(bot, talentId)` / `GetBotTalentEffectValue(...)`）。
2. 把 `RogueTalents[]` 的 `{spec,minLvl,maxLvl,auraId}` 改为 `{talentId, rank, auraId(可反查)}`，`ApplyClassPassives()` 循环条件改为「构筑中该天赋 rank >= 目标 rank」。
3. **同批次删除** B/C 类中天赋来源的 `lvl >=` + 数值，改为从构筑反查（见第 5 节台账逐项）。
4. 雕文先从天赋表剥离（`GLYPH_BACKSTAB` 移入雕文流程），天赋表只留天赋。

### 6.3 阶段 D：接入雕文

1. 引入 `HasBotGlyphEquipped(bot, glyphId)` / `GetBotGlyphEffectValue(...)`。
2. 把第 5.3 节 23 处纯 B 类雕文逐项改为「槽位查询 + 数值反查」，**先删旧硬编码再让新层提供**。
3. 20 级前 0 槽、20 级起 6 槽（方案 5.3），与天赋截断相互独立。

### 6.4 阶段 D′：零残留复查

- `ApplyClassPassives()` 内不再有 `level >=`/`spec ==` 的天赋/雕文条件；
- `ApplyClass*` / `SpellHitTarget` 内不再有台账标记为天赋/雕文的数值字面量；
- 命中项须能在第 5.2 节白名单找到对应条目。
- 基线对账：改造前 `bot_rogue_ai.cpp` 共 **83** 行含 `lvl >=` / `level >=` 等级门（实测 `grep -c`）；改造后剩余行数 = 83 −（已迁移行数）。台账「已删除旧实现」条目覆盖的出现位置数应等于迁移量。
