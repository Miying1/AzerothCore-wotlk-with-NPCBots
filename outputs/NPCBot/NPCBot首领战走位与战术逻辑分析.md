# NPCBot Boss 战走位与战术逻辑分析

## 1. 结论摘要

当前 NPCBot 的 Boss 战能力不是一个统一的“Boss 战术引擎”，而是由以下几层叠加形成：

1. **通用角色 AI**：坦克、治疗、近战 DPS、远程 DPS 各自执行职业技能优先级。
2. **通用移动与危险区系统**：跟随队形、追击、绕背、避开正面、坦克调整朝向、AOE 安全点搜索。
3. **团队管理逻辑**：进场延迟、主坦/副坦角色、团队标记选怪、仇恨门槛。
4. **公共战术能力**：打断、驱散、净化、控制、治疗、减伤和复活。
5. **少量 Boss 硬编码**：针对骨刺、冰墓、瓦格里、污染之核等机制进行目标切换或物件交互。
6. **玩家手动控制**：通过 `sendto`、`stay` 等命令完成自动 AI 无法稳定处理的定点站位。

因此，它能较好处理“坦克拉住、近战绕背、远程分布、躲部分地面技能、优先机制目标”这一类战斗，但对需要严格阶段状态机、同步集合/分散、路径规划、打断轮次、换坦层数和精确站位槽的 Boss，自动化程度仍不够。

## 3. 当前走位逻辑

### 3.1 非战斗跟随队形

`_calculatePos()` 根据角色位和跟随对象计算基础队形：

- **坦克**：通常站在主人前方约 3.5 码，并按角色槽位向左右分散。
- **远程角色**：位于主人后方，按槽位展开，避免全部叠在同一点。
- **近战 DPS**：主要分布在主人两侧。
- **其他角色**：使用默认侧方或后方跟随位置。

这套队形的作用主要是减少移动时的重叠，并让坦克更早接触敌人；它不是针对具体 Boss 房间或机制生成的固定站位图。

### 3.2 战斗中的基础移动决策

`GetInPosition()` 的核心分流是：

```cpp
if (IsRanged() || (!IAmFree() && !GetAoeSpots().empty()))
    CalculateAttackPos(...);
else
    BotMovement(BOT_MOVE_CHASE, nullptr, newtarget);
```

含义如下：

- **普通近战且附近没有已识别危险区**：直接追击目标。
- **远程角色**：计算一个满足射程、视线、主人距离和危险区限制的攻击位置。
- **存在 AOE 危险区时**：即使是近战，也会进入位置计算流程，尝试寻找安全攻击点。

### 3.3 近战绕背

`MoveBehind()` 允许非坦近战尝试移动到目标背面，从而：

- 避免正面顺劈和部分正面技能；
- 减少招架；
- 满足盗贼等职业的背后技能条件。

以下情况通常不会绕背：

- Bot 是远程角色；
- Bot 处于不可移动命令状态；
- Bot 正在载具中或被控制；
- Bot 是当前坦克且目标正在攻击它；
- 目标不在近战范围；
- 当前方向关系不满足调整条件。

该设计正确地区分了“坦克保持 Boss 正面”和“近战 DPS 绕背”。

### 3.4 坦克朝向与聚怪

`AdjustTankingPosition()` 会评估有多少近战敌人位于坦克背后，并尝试移动到新的候选点，使更多敌人进入正面区域。

候选位置会检查：

- 与目标的相对位置；
- 视线；
- 是否落入已识别 AOE；
- 当前是否允许移动。

其目标不是精确地把 Boss 固定朝向某个房间方向，而是降低坦克背后受击的概率，并改善多目标聚怪。

### 3.5 远程攻击位置

`CalculateAttackPos()` 综合考虑：

- 职业或技能需要的攻击距离；
- 与目标的距离；
- 与主人的距离；
- 目标和候选点之间的 LOS；
- 已识别的 AOE 危险区；
- 是否需要避开目标正面；
- 是否仍能在候选点攻击目标。

当配置使用 `BOT_ATTACK_ANGLE_AVOID_FRONTAL_AOE` 时，远程角色面对非玩家控制目标，会尽量离开目标正面扇区。

### 3.6 远程被 Boss 盯上时的带怪行为

远程 Bot 成为目标当前受害者时，会尝试把敌人带向坦克或主人，而不是继续向远处风筝。

这是一个实用的仇恨修复动作，但当前坦克候选条件中存在疑点：

```cpp
IsTank(c) && c->GetBotAI()->HasRole(BOT_ROLE_DPS)
```

它要求候选 NPCBot 同时被识别为坦克且拥有 DPS role，可能漏掉纯坦克角色，使远程 Bot 无法找到最合理的接怪对象。

### 3.7 AOE 危险区识别

`CalculateAoeSpots()` 会扫描主人附近约 60 码范围内的敌方 `DynamicObject`，识别具有以下效果的区域：

- 周期伤害；
- 百分比伤害；
- 法力燃烧；
- 吸血；
- 触发法术；
- 部分 `DUMMY` Aura。

此外还硬编码识别了若干副本危险物体或生物，例如：

- 熔火之心：Hot Coal；
- 安其拉废墟：Sand Trap；
- 安其拉神殿：Mutating Bug 爆炸；
- 鲜血熔炉：Proximity Bomb；
- 地狱火城墙：Liquid Fire；
- 奥金尼地穴：Fiery Blast；
- 永恒之眼：Static Field；
- 魔导师平台：Phoenix / Arcane Sphere；
- 祖阿曼：Fire Bomb；
- 乌特加德城堡：Shadow Axe；
- 冰冠堡垒：Ooze Puddle。

`BotMgr` 在队伍进入战斗时统一计算并共享危险区，避免每个 Bot 完全独立扫描。

### 3.8 AOE 安全点搜索

`CalculateAoeSafeSpots()` 使用距离和角度逐步增加的采样方式，在周围搜索不落入危险区的候选点。`CalculateAttackPos()` 再从候选点中优先选择：

1. 能继续攻击当前目标的安全点；
2. 距离当前位置较近的点；
3. 视线和主人距离可接受的点。

现有实现更接近“螺旋采样”，而不是严格的同心圆搜索：

```cpp
float aoedist = 0.f;

for (...)
{
    float aoeangle = 0.0f;
    for (...)
    {
        aoedist += distdelta;
        aoeangle += angledelta;
    }
}
```

`aoedist` 没有在外层循环重置，因此候选距离会持续增大。这未必必然错误，但搜索分布不均匀，近距离可用点的覆盖率不足。

### 3.9 无安全点时的回退

如果存在危险区但找不到安全点，受主人控制的 NPCBot 会直接把主人位置作为回退点：

```cpp
else if (!aoespots.empty() && !IAmFree())
{
    pos.Relocate(master);
    force = true;
    return;
}
```

如果主人本身也在危险区，这会把 Bot 拉回同一个危险位置。当前逻辑没有再次验证主人位置是否安全。

### 3.10 手动定点控制

`botcommands.cpp` 支持玩家：

- 将指定 Bot 发送到点击位置；
- 让 Bot 返回上一个位置；
- 标记多个发送点；
- 切换 `STAY` 等待状态。

因此，当前系统对严格站位 Boss 的实际使用方式通常是“自动行为为主，关键位置由玩家手动补充”。

## 4. 当前战术逻辑

### 4.1 角色分工

NPCBot 使用以下主要角色位：

```cpp
BOT_ROLE_TANK
BOT_ROLE_TANK_OFF
BOT_ROLE_DPS
BOT_ROLE_HEAL
BOT_ROLE_RANGED
```

一个 Bot 可以同时具备多个 role，例如远程 DPS 同时拥有 `DPS` 和 `RANGED`。战斗决策会根据 role 决定是否嘲讽、治疗、绕背、保持距离或参与输出。

### 4.2 主坦与副坦

`CanTauntTarget()` 允许坦克在以下场景接管目标：

- 目标正在攻击非坦成员；
- 当前坦克生命值过低；
- 团队标记指定目标应由主坦或副坦负责；
- 当前目标没有嘲讽免疫或控制冲突。

`CanTauntDistantTarget()` 对远程嘲讽更保守。高等级 Dungeon Boss 和 World Boss 默认禁止部分自动远程换嘲，以避免随机条件导致 Boss 错误转头。

这说明当前系统具备基础救场和主副坦分工，但没有通用的“Debuff 达到 N 层后换坦”机制。

### 4.3 团队标记驱动的目标分配

配置支持以下团队图标掩码：

```ini
NpcBot.HealTargetIconMask
NpcBot.TankTargetIconMask
NpcBot.OffTankTargetIconMask
NpcBot.DPSTargetIconMask
NpcBot.RangedDPSTargetIconMask
NpcBot.NoDPSTargetIconMask
```

这些配置可以让团队标记承担简易战术指令：

- 指定主坦目标；
- 指定副坦目标；
- 指定全体 DPS 或远程 DPS 的集火目标；
- 标记禁止攻击目标；
- 标记优先治疗单位。

它是当前系统中最通用、最容易由玩家控制的团队战术接口。

### 4.4 进场延迟和仇恨门槛

`BotMgr::PropagateEngageTimers()` 允许通过以下配置延迟非坦克参战：

```ini
NpcBot.EngageDelay.DPS
NpcBot.EngageDelay.Heal
```

坦克不会被延迟。Raid World Boss 还存在额外仇恨检查：非坦克会等待当前受害者建立至少以下仇恨后再开始行动：

```cpp
std::min<uint32>(50000, victimMaxHealth / 2)
```

优点是可减少开怪瞬间 OT；不足是配置注释表明进场延迟会影响除 PvP 外的所有战斗，不只影响 Boss，粒度偏粗。

### 4.5 打断

`CastingUnitCheck` 会搜索正在施法的敌人，并检查：

- 距离和相位；
- 是否为合法敌对单位；
- 当前是否确实在施法；
- 是否免疫打断或沉默；
- 职业技能是否可用。

之后各职业 AI 根据自身技能进行打断。当前模式是“各 Bot 独立寻找并尝试”，缺少团队级的打断排班和预约，可能出现多人同时打断同一法术。

### 4.6 驱散、净化和激怒移除

公共筛选器包括：

- `HostileDispelTargetCheck`：查找敌方可驱散或可偷取的增益；
- `TranquilTargetCheck`：查找可移除激怒的敌人；
- 各职业友方净化逻辑：移除中毒、疾病、诅咒或魔法减益。

同样，这些决策主要由各职业独立进行。没有统一的“由谁负责哪种驱散、避免重复施法”的团队协调器。

### 4.7 控制

代码提供多类公共目标检查器：

- `PolyUnitCheck`；
- `FearUnitCheck`；
- `StunUnitCheck`；
- `RootUnitCheck`。

控制逻辑会考虑目标类型、距离、免疫、已有控制和战斗关系。Boss 本体通常免疫大部分控制，因此这些能力主要用于 Boss 战中的小怪处理。

### 4.8 治疗、减伤与复活

治疗 Bot 会根据友方生命值、职业技能、距离和当前角色进行：

- 单体治疗；
- 群体治疗；
- 驱散；
- 紧急保命；
- 团队减伤；
- 战斗结束后的复活。

但治疗和团队减伤仍主要基于局部状态和随机门槛，没有统一的“预计伤害事件时间轴”。遇到固定时间的大范围高伤技能时，无法像专用 Boss 状态机那样提前预铺治疗或轮换减伤。

### 4.9 已实现的 Boss 专用机制

当前代码确实包含一些硬编码 Boss 处理，而不是完全依赖通用 AI。

#### 冰冠堡垒

- **玛洛加尔领主**：DPS 优先攻击 Bone Spike，营救被穿刺目标。
- **辛达苟萨**：根据空中阶段和 Ice Tomb 状态处理冰墓；部分阶段会控制攻击行为。
- **巫妖王**：远程 DPS 优先处理 Valkyr，其次处理 Ice Sphere。
- **冰冠堡垒软泥机制**：危险区系统识别 Ooze Puddle。
- **Sister Svalna 事件**：处理 Infernal Spear。

#### 其他团队副本

- **黑翼之巢 Bloodlord Lashlayer 区域**：盗贼处理 Suppression Device。
- **太阳之井 M’uru**：萨满或牧师驱散 Dark Fiend。
- **黑暗神殿 Naj’entus**：处理 Impaling Spine。
- **毒蛇神殿 Lady Vashj**：处理 Tainted Core 和 Shield Generator。

这些逻辑证明代码已经具备机制扩展入口，但实现散落在通用 `bot_ai.cpp` 中，难以维护、测试和系统扩展。

## 5. 当前实现的主要问题

### 5.1 鲜血熔炉英雄难度炸弹 ID 疑似写错

当前数组为：

```cpp
static const std::array<uint32, 2> ProximityBombIds =
    { GAMEOBJECT_PROXIMITY_BOMB_N, GAMEOBJECT_PROXIMITY_BOMB_N };
```

但 `botcommon.h` 同时定义：

```cpp
GAMEOBJECT_PROXIMITY_BOMB_N = 181877,
GAMEOBJECT_PROXIMITY_BOMB_H = 182607,
```

第二项大概率应使用 `GAMEOBJECT_PROXIMITY_BOMB_H`。否则英雄难度炸弹可能无法被识别为危险区。

### 5.2 远程带怪可能找不到纯坦克

候选坦克条件要求同时具有 DPS role，可能把纯坦排除在外。这会降低远程 OT 后的归位能力。

### 5.3 安全点只验证终点，不验证移动路径

候选终点安全并不代表移动路径安全。Bot 可能为了前往安全点而穿过火墙、黑水或其他高伤区域。

### 5.4 找不到安全点时盲目回主人位置

主人可能同样位于 AOE 中，回退逻辑缺少安全性复核和替代策略。

### 5.5 安全点采样不均匀

距离累计不在外层循环重置，使搜索偏向持续向外扩张；近距离环形区域覆盖不足，也没有基于导航网格评估可达性。

### 5.6 Boss 判定和危险度判定不统一

部分逻辑使用：

- `IsDungeonBoss()`；
- `isWorldBoss()`；
- Creature rank；
- 地图是否为 Raid；
- 具体 Entry ID。

不同条件散落在多处，容易产生某些 Boss 被一段逻辑识别、却被另一段逻辑遗漏的情况。

### 5.7 关键战术仍受随机门槛影响

打断、嘲讽、保命、走位调整等部分逻辑带有 `Rand()` 概率。随机性可让普通战斗更自然，但在致命 Boss 机制上会导致不可预测失败。

### 5.8 缺少团队级资源协调

当前每个 Bot 大多独立判断，容易发生：

- 多个 Bot 同时打断同一法术；
- 多个治疗同时驱散同一目标；
- 多个坦克同时嘲讽；
- 多个治疗同时交大技能；
- 控制技能重复覆盖。

### 5.9 Boss 特判和通用 AI 高耦合

具体副本机制散落在 `bot_ai.cpp` 的目标选择、非攻击目标处理和危险区扫描中。继续增加 Boss 时，文件会越来越大，也难以写单元测试。

## 6. 优化建议与优先级

## P0：优先修复明确缺陷

### 6.1 修正英雄难度 Proximity Bomb ID

将第二个 normal ID 改为 heroic ID，并核实普通/英雄地图中的实际 GameObject entry。

预期收益：恢复鲜血熔炉英雄难度炸弹规避。

### 6.2 修正远程带怪的坦克筛选

候选条件应以“有效坦克且可接怪”为核心，而不是要求坦克同时拥有 DPS role。还应优先选择：

1. 当前主坦；
2. 正在攻击该敌人的副坦；
3. 距离最近、存活且可移动的坦克；
4. 最后才回到主人。

### 6.3 无安全点时禁止直接采用未经检查的主人位置

回退顺序建议改为：

1. 已验证安全且可达的主人附近位置；
2. 上一个安全位置；
3. 与危险区中心相反方向的紧急撤离点；
4. 原地停留并使用保命技能；
5. 最后才考虑主人当前位置。

---

## P1：提高 Boss 战可靠性

### 6.4 引入路径级危险检测

不能只判断目标点是否位于 AOE，还应检查从当前位置到目标点的路径是否穿越危险区。

可行方案：

- 对导航路径进行分段采样；
- 每个采样点检查危险区；
- 将穿越危险区的距离和预计伤害加入路径代价；
- 对致死型区域直接判定路径不可用。

### 6.5 重构安全点采样

建议采用分层同心圆或导航网格采样：

- 每个半径独立重置角度；
- 优先搜索近距离点；
- 根据角色设置最大移动距离；
- 远程优先保持射程，近战优先保持接敌能力；
- 验证 LOS、可达性、坡度和路径危险度。

### 6.6 建立统一 Boss/机制上下文

建立类似 `BotEncounterContext` 的共享结构，统一提供：

- 当前地图和 Encounter；
- Boss GUID、Entry 和阶段；
- 当前主坦、副坦和仇恨目标；
- 危险区列表；
- 机制目标列表；
- 团队集合点、分散点和安全区；
- 下一次关键施法及剩余时间。

所有职业 AI 从同一上下文读取信息，避免各处分散判断 Boss 类型。

### 6.7 关键行为由危险度评分替代随机门槛

建议对行为建立优先级评分：

```text
致死机制打断 > 离开致死 AOE > 紧急嘲讽 > 紧急治疗
> 机制目标切换 > 驱散 > 普通轮转 > 随机表现
```

对可致死事件取消或大幅降低随机性；随机仅用于同优先级候选之间的微调。

### 6.8 团队级打断协调

建立打断预约：

- 为每个敌方施法维护一个打断 owner；
- 按距离、技能是否就绪、打断类型和剩余施法时间排序；
- 第一位失败后立即切换下一位；
- 避免多人同时浪费冷却。

同一协调方式也可用于驱散、战复、控制和坦克嘲讽。

### 6.9 增加换坦状态机

通用换坦至少需要支持：

- 指定 Aura ID 和层数阈值；
- 当前坦克层数；
- 副坦是否存活、可达、嘲讽就绪；
- 嘲讽成功后原坦停止高仇恨技能；
- Debuff 消失后重新进入轮换。

这样才能稳定处理 WotLK 中大量层数换坦机制。

## P2：架构与可扩展性优化

### 6.10 将 Boss 特判拆成 Encounter 战术模块

建议不要继续把机制条件直接堆入 `bot_ai.cpp`，而是按副本/Encounter 注册模块，例如：

```text
NpcBots/Encounters/IcecrownCitadel/
NpcBots/Encounters/Ulduar/
NpcBots/Encounters/TrialOfTheCrusader/
```

每个模块可实现：

- 阶段识别；
- 机制目标优先级；
- 危险区补充；
- 坦克规则；
- 集合/分散规则；
- 职业专属交互；
- 机制开始和结束条件。

### 6.11 增加团队站位槽

为常见机制提供动态站位槽：

- 近战背后扇形槽；
- 远程环形分散槽；
- 治疗中后场槽；
- 主坦和副坦朝向槽；
- 集合点；
- 左右分组点；
- 传染或连线机制隔离点。

槽位需支持占用和释放，避免多个 Bot 选择同一个“安全点”。

### 6.12 引入阶段状态机

针对复杂 Boss 建立：

```text
Pull → Phase 1 → Transition → Adds → Burn → Enrage/End
```

状态变化可以由 Boss 血量、Aura、施法、召唤物、GameObject 和 Encounter 状态触发。这样 Bot 才能提前改变站位和保留技能，而不是机制发生后才被动响应。

### 6.13 AOE 与目标扫描缓存

当前已经由 `BotMgr` 共享部分 AOE 数据，可继续扩展为：

- 每个队伍每个更新周期只扫描一次；
- 缓存敌方施法、可驱散 Aura、机制目标和可交互物；
- 各 Bot 只做角色相关的排序和选择；
- 对缓存设置短生命周期，避免过期 GUID。

### 6.14 增加可观测性和测试

建议增加可配置调试输出：

- 当前 Encounter 和阶段；
- 选择某个位置的原因；
- 放弃候选点的原因；
- 打断/驱散 owner；
- 当前主坦、副坦和换坦状态；
- 机制目标优先级。

测试重点：

- AOE 点内外判断；
- 安全点和路径选择；
- 主坦/副坦目标分配；
- Boss 仇恨门槛；
- 打断预约；
- Aura 层数换坦；
- 特定 Encounter 的阶段切换。

## 7. 推荐实施顺序

### 第一阶段：低风险修复

1. 修正英雄 Proximity Bomb ID。
2. 修正远程带怪的坦克筛选。
3. 主人位置回退前增加安全检查。
4. 修正并补测安全点采样分布。

### 第二阶段：可靠性提升

1. 路径穿越 AOE 检查。
2. 关键打断、驱散、换坦去随机化。
3. 团队级技能预约。
4. 统一 Boss 和 Encounter 上下文。

### 第三阶段：Boss 战术框架

1. 拆分 Encounter 模块。
2. 增加阶段状态机。
3. 增加分散、集合和坦克朝向站位槽。
4. 逐副本迁移现有硬编码机制。

## 8. 总体评价

当前 NPCBot Boss 战 AI 已经超过简单的“跟随主人并自动放技能”：它具备角色队形、绕背、坦克朝向、危险区识别、安全点搜索、仇恨等待、主副坦、团队标记和少量副本机制处理。

它的主要瓶颈不是缺少单个职业技能，而是缺少一个统一的团队 Encounter 层。现有 Bot 能各自做出许多局部正确决定，但难以保证全队在同一时刻执行一致的 Boss 战术。

最值得优先投入的方向是：

1. 修复已确认的危险区和坦克筛选缺陷；
2. 把“终点安全”升级为“路径安全”；
3. 将随机的关键动作改为危险度驱动；
4. 增加团队级打断、驱散和换坦协调；
5. 最终把散落的 Boss 特判迁移到可扩展的 Encounter 状态机。
