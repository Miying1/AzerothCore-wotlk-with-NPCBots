# 盗贼 BOT 战斗逻辑与基线差异分析

## 1. 对比范围

- 当前分支：`merge_test2_from_npcbots`
- 当前提交：`024831590`（`HEAD`）
- 权威基线：`upstream/npcbots_3.3.5@d914b8288`
- merge-base：`d914b8288`，当前分支在基线上前进 136 个提交
- 对比文件：`src/server/game/AI/NpcBots/bot_rogue_ai.cpp`
- 差异规模：7 行新增、6 行删除
- 工作树状态：该文件没有未提交修改

`upstream/npcbots_3.3.5@d914b8288` 正好是当前 `HEAD` 的 merge-base，因此用它作为基线不会把尚未合并的上游未来修改混进结论。

## 2. 总体结论

当前盗贼 AI 与基线高度一致。忽略空白后，只有两处战斗语义发生变化：

1. `Killing Spree`（杀戮盛筵）取消“自身被多个敌人攻击时允许对低血目标释放”的兜底；
2. `Fan of Knives`（刀扇）在至少 3 个近身目标且能量不足时直接结束本次攻击决策，进入蓄能状态。

第二处是影响更大的改动：它不只是让刀扇等待能量，而是会阻断同一轮后续的连击点生成技能，包括还击、鬼魅攻击、出血、影袭、背刺和毁伤。因此当前版本更强制地坚持三目标 AOE，但可能降低优先目标伤害、连击点生成、坦克模式生存和低能量阶段的动作连续性。

除上述两处外，下列逻辑与基线一致：

- 战斗更新顺序和目标选择；
- 潜行、消失和暗影之舞起手；
- 脚踢、凿击、致盲、肾击等打断与控制；
- 切割、割裂、毒伤/刺骨等终结技；
- 能量读取、菊花茶和冲动；
- 闪避、佯攻、暗影斗篷等生存逻辑；
- 背刺/毁伤/影袭等武器与专精适配；
- 毒药和非战斗附魔逻辑。

## 3. 差异一：杀戮盛筵更保守

当前文件 `bot_rogue_ai.cpp:383-386`：

```cpp
if (IsSpellReady(KILLING_SPREE_1, diff) && !stealthed && !shadowdance && HasRole(BOT_ROLE_DPS) &&
    Rand() < (70 - energy) && dist < 10 && GetHealthPCT(me) > 25 && (!CCed(mytar) || dist > 5) &&
    (mytar->getAttackers().size() < 4 || mytar->GetMaxHealth() > me->GetMaxHealth() * 2) &&
    mytar->GetHealth() > me->GetMaxHealth() / 2)
```

基线对应条件：

```cpp
(mytar->GetHealth() > me->GetMaxHealth() / 2 || me->getAttackers().size() > 1)
```

### 行为变化

基线允许以下两类情况触发：

- 当前目标生命值高于盗贼最大生命值的 50%；
- 即使目标已低血，只要盗贼正被至少 2 个单位攻击，也可以触发。

当前版本删除了第二个分支，所以无论盗贼承受多少敌人围攻，只要目标当前生命值不高于盗贼最大生命值的一半，就不会使用杀戮盛筵。

注意这里比较的是目标的“绝对当前生命值”和盗贼的“最大生命值”，不是目标生命百分比。例如盗贼最大生命 20,000 时，目标低于或等于 10,000 当前生命便会被视为“不值得释放”，即使目标自身仍有很高的生命百分比。

### 实战影响

- 多敌围攻时减少杀戮盛筵的应急爆发和短暂无目标/位移价值；
- 更少把长冷却浪费在绝对血量较低的目标上；
- 击杀收尾更依赖普通技能和终结技；
- 对小怪群偏保守，对高血量 Boss 基本无影响；
- 原有 `Rand() < 70 - energy` 仍使其偏向低能量时触发，本次没有改变该资源倾向。

### 判断

这是明确的策略调整，不像代码错误。总体取向是“保留杀戮盛筵给绝对血量较高的目标”，代价是删除基线针对多敌围攻的兜底。

## 4. 差异二：刀扇改为强制蓄能

当前文件 `bot_rogue_ai.cpp:680-695`：

```cpp
if (!HasRole(BOT_ROLE_DPS))
    return;
std::list<Unit*> targets;
GetNearbyTargetsList(targets, 7.f, 1);
//Fan of Knives
if (GetSpell(FAN_OF_KNIVES_1) &&
    Rand() < 35 + 40 * hasAdrenalineRush + 50 * hasBladeFlurry)
{
    std::list<Unit*> targets;
    GetNearbyTargetsList(targets, 7.f, 1);
    if (targets.size() > 2 && energy < ecost(FAN_OF_KNIVES_1))
        return;
    if (targets.size() > 2 && energy >= ecost(FAN_OF_KNIVES_1) && doCast(me, GetSpell(FAN_OF_KNIVES_1)))
        return;
}
```

基线核心逻辑：

```cpp
if (GetSpell(FAN_OF_KNIVES_1) && energy >= ecost(FAN_OF_KNIVES_1) && Rand() < chance)
{
    std::list<Unit*> targets;
    GetNearbyTargetsList(targets, 7.f, 1);
    if (targets.size() > 2 && doCast(me, GetSpell(FAN_OF_KNIVES_1)))
        return;
}
```

### 4.1 基线行为

当能量不足以施放刀扇时，刀扇分支直接不成立，AI 会继续向下检查单体连击点生成技能：

1. 还击；
2. 鬼魅攻击；
3. 出血；
4. 影袭；
5. 背刺/毁伤。

也就是说，基线是“刀扇有能量就尝试，否则继续单体轮转”。

### 4.2 当前行为

当前先通过随机门槛，再统计 7 码目标。如果附近至少 3 个目标但能量不足，会直接 `return`，本轮不再尝试任何后续生成技能。

因此它实现的是：

> 三目标及以上时，只要本轮随机判定想用刀扇，就停下其他技能等待刀扇能量。

这是一种显式的 AOE 蓄能策略。

### 4.3 触发概率

`Rand()` 并非每次条件独立生成，而是 `GlobalUpdate()` 每轮生成一次并在本轮复用。自由 BOT 的常见范围为 0–100；有主人的队伍 BOT 上限还会随 NPCBot 数量略增。

名义随机门槛为：

- 普通状态：`Rand() < 35`；
- 冲动：`Rand() < 75`；
- 剑刃乱舞：`Rand() < 85`；
- 两者同时存在：门槛 125，通常近似必进。

所以群怪低能量时的停手并非每轮必然，但在冲动/剑刃乱舞期间会非常频繁，二者同时存在时尤其明显。

### 4.4 实战影响

正面效果：

- 三目标以上更容易尽快攒够刀扇能量；
- 避免刚有一点能量就被影袭、出血或毁伤消耗；
- AOE 输出意图更稳定，尤其在冲动或剑刃乱舞期间。

负面效果：

- 低能量群怪阶段可能出现技能停顿；
- 主目标连击点生成降低，连带延后切割、肾击、割裂、毒伤/刺骨；
- 还击也会被跳过，浪费短暂的招架反应窗口；
- 坦克模式的鬼魅攻击可能被跳过，损失闪避增益和生存价值；
- 刀扇随机门槛未通过时仍会继续单体轮转，因此行为会在“蓄能停手”和“正常单体技能”之间随机切换；
- 逻辑没有判断目标质量、控制状态或是否应避免破控，只按附近目标数量决策。

### 4.5 重复扫描与无效代码

当前在 `682-683` 先构造并填充一次 `targets`，随后在刀扇分支的 `690-691` 又声明同名局部变量并重新扫描。外层列表从未被读取，属于无效工作：

```cpp
std::list<Unit*> targets;
GetNearbyTargetsList(targets, 7.f, 1); // 结果未使用
```

影响主要是：

- 每轮走到该位置都会额外做一次 7 码目标扫描，即使没有学会刀扇或随机门槛未通过；
- 内层同名变量遮蔽外层变量，可读性较差；
- 没有改变最终目标数量判断结果，但增加不必要开销。

此外，`bot_rogue_ai.cpp:683` 存在行尾空格，`git diff --check` 会报错。

### 判断

“能量不足直接 return”明显是有意添加的 AOE 蓄能策略；但外层目标扫描是实现残留，应删除。是否保留强制蓄能取决于设计目标：

- 若追求三目标以上刀扇优先，策略可保留，但建议避免阻断还击和坦克鬼魅攻击；
- 若追求动作连续性和主目标连击点，应恢复基线的能量前置条件。

## 5. 未发生变化的战斗框架

当前 `UpdateAI()` 和 `Attack()` 的主要优先级仍与基线相同：

1. 更新连击点和能量；
2. 公共状态、载具、药水、种族技能；
3. 非战斗毒药维护；
4. 打断队列；
5. 可用物品、疾跑、暗影斗篷、消失；
6. 目标检查；
7. 致盲、伺机待发、嫁祸诀窍；
8. 进入 `Attack()`；
9. 潜行、鲜血渴求、预谋、杀戮盛筵、控制和生存技能；
10. 近战距离检查与走背；
11. 菊花茶、佯攻、冲动；
12. 割裂和终结技；
13. 暗影之舞及潜行起手；
14. 刀扇；
15. 单体连击点生成技能。

两处定制都位于这一固定优先级链中，因此 `return` 的位置就是实际行为影响的关键。

## 6. 风险排序与建议

### 高优先级：复核刀扇低能量 `return`

这是最大的语义差异。建议至少做以下一种处理：

1. **恢复基线**：把 `energy >= ecost(FAN_OF_KNIVES_1)` 放回外层条件，能量不足时继续单体轮转；
2. **保留蓄能但保护高价值技能**：将还击、坦克模式鬼魅攻击放到刀扇蓄能判断之前；
3. **保留纯 AOE 蓄能**：明确注释设计意图，并确保只扫描一次目标列表。

### 中优先级：确认杀戮盛筵设计意图

若期望多敌围攻时仍可利用杀戮盛筵爆发/位移，应恢复：

```cpp
|| me->getAttackers().size() > 1
```

若期望严格避免对低绝对血量目标浪费冷却，当前逻辑可以保留。

### 低优先级：清理实现质量

- 删除 `682-683` 未使用的外层目标列表；
- 修复 `683` 行尾空格；
- 按项目风格给二元运算符留空格；
- 将单行 `return` 拆成符合项目可读性的多行条件块。

## 7. 最终评价

当前盗贼版本不是完整轮转重写，而是非常小的定制补丁：

- `杀戮盛筵`：从“高血目标或自身被围攻”收窄为“仅高血目标”；
- `刀扇`：从“能量够才考虑，否则继续单体”改为“群怪时概率性停手蓄能”。

前者是偏保守的冷却管理，后者是偏强制的 AOE 资源管理。真正需要优先测试的是三目标以上、低能量场景，特别是战斗专精开启冲动/剑刃乱舞以及盗贼承担坦克职责时。
