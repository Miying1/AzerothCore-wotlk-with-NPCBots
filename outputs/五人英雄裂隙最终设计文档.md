# 五人英雄裂隙最终设计文档

> 适用版本：AzerothCore WotLK 3.3.5a + NPCBots
>
> 本文是五人英雄裂隙的唯一最终设计文档。此前裂隙传送、简化配置、入口解耦、Boss模板和出口门的重复设计均以本文为准。

## 1. 最终设计目标

五人英雄裂隙是海加尔山开放世界中的旧世界副本挑战入口。玩家从海加尔山的裂隙、入口NPC或其他受支持的Gossip入口发起挑战，选择T1、T2或T3后，由服务器随机选择一个启用的旧世界副本Boss，创建该Boss对应的实例场景，并将队伍传送到Boss战斗区域。

每场裂隙只激活一个Boss，不要求玩家清理副本小怪，也不把入口永久绑定到某一张副本或某一个Boss。

核心原则：

- 最多5个战斗席位，允许少于5人进入；
- Boss不根据真实玩家数量、NPCBot数量或Free Bot数量动态缩放；
- 同一个Boss的T1/T2/T3生物Entry全部使用同一个Boss C++脚本；
- 该Boss的强度和技能差异全部在这一份脚本内通过T1/T2/T3控制；
- 实例运行状态只存服务器内存，不写运行态数据库；
- T1/T2/T3分别使用出口GameObject Entry 100500/100501/100502和模型7148/8196/8197，但共用同一个 `rift_exit_portal` 脚本与固定对话“离开...”；本场只记录发起入口对话者的位置，所有通过出口门离开的玩家都返回这一处共享位置；
- 不伪装LFG，不引入LFG随机本状态、投票踢人、逃亡者、补位Bot等额外耦合。

## 2. 入口与随机流程

### 2.1 入口解耦

入口对象不负责绑定某一副本或Boss，只负责让队长选择Tier并发起挑战。可支持：

- 海加尔山固定位置的裂隙GameObject；
- 选择Tier的入口NPC；
- 后续扩展的其他CreatureScript或GameObjectScript入口。

不同入口统一调用同一个启动服务，不在各自Gossip脚本中重复编写副本随机、Boss随机、实例创建、传送、返回点和出口门逻辑。

### 2.2 Gossip选项

入口提供以下固定选项：

```text
进入 T1
进入 T2
进入 T3
取消
```

客户端Action只表达Tier选择，不携带可信的Boss ID、地图ID、实例ID、坐标或返回坐标。服务器收到选择后，从启用配置中执行随机：

```text
玩家/队长选择Tier
    ↓
校验队伍和战斗席位
    ↓
从配置表1筛选 enabled=1 的Boss
    ↓
联结配置表2中相同 boss_id + tier 的行
    ↓
按 map_id 分组并等概率随机一个副本
    ↓
在该副本的合法候选中随机一个Boss
    ↓
创建或加入对应 map_id 的普通 InstanceMap
    ↓
在Boss生成点召唤该Tier的 entry_id
    ↓
将真实玩家传送到该Tier最终玩家传入点
```

候选Boss必须同时满足：

- 配置表1和表2均存在；
- `enabled=1`；
- 选择Tier对应的 `entry_id` 存在；
- `map_id` 可创建实例；
- Boss生成点通过地图坐标、高度和碰撞校验；
- 玩家传入点通过地图坐标、安全高度、可行走和距离校验。

如果候选无效，直接排除并重新随机，不能使用任意默认副本入口或默认Boss坐标兜底。

## 3. 队伍和NPCBot规则

### 3.1 战斗席位

- 队伍最多5个战斗席位；
- 允许1至5个真实玩家进入；
- 不按队伍人数改变Boss血量、伤害、技能数量或技能强度；
- NPCBot不作为裂隙Boss倍率计算依据。

### 3.2 玩家传送

只有真实玩家由裂隙模块主动传送。流程为：

1. 发起入口对话的玩家确认Tier；
2. 只记录该对话发起者在进入裂隙前的位置，作为本场全队共享返回点；不记录其他队员各自的位置；
3. 服务器创建新的普通副本实例并取得其 `InstanceSave`；
4. 在任何成员开始传送前，将全部真实玩家临时绑定到同一个 `map_id + instanceId`，避免远距离传送确认竞态导致成员分流；
5. 再将全部真实玩家传入该实例，并在配置的唯一玩家传入点周围分配安全偏移；
6. Boss在配置的Boss生成点召唤并进入战斗准备流程。

### 3.3 NPCBot进入

- 已经加入队伍并且跟随主人的玩家NPCBot，不由裂隙脚本直接传送；
- 主人完成远距离传送后，继续使用现有NPCBot跟随和 `BotMgr::OnTeleportFar` 机制自动进入；
- Free Bot不进入裂隙；
- 不为NPCBot额外分配独立的玩家传入偏移点；
- 不因为Bot是否及时进入而重新计算Boss强度。

## 4. 副本与Boss坐标

### 4.1 副本场景

旧世界副本通常没有可直接复用的原生英雄地图难度，因此使用对应普通副本的 `map_id` 作为场景外壳。T1/T2/T3不依赖核心的客户端地下城难度分支，而由裂隙配置、独立Boss Entry和Boss脚本控制。

### 4.2 Boss生成点

配置表2中的 `boss_spawn_x/y/z/o` 使用现有副本原版Boss的实际生成坐标。每场只召唤新的T1/T2/T3 Entry，原版静态Boss不参与本场战斗。

Boss生成点应在导入配置前完成：

- `map_id`一致性检查；
- `IsValidMapCoord`检查；
- 地图高度和碰撞检查；
- 与玩家传入点的距离和可达性检查。

### 4.3 玩家唯一传入点

玩家传入点不是代码常量，由用户或运营者为每个Boss提供并写入配置。该点应位于Boss房间内安全、可行走的位置，可以与Boss生成点不同。

同一场小队使用同一个配置传入点。真实玩家在该点周围按任意方向偏移1至2码：

```cpp
angle = random(0.0f, 2.0f * PI);
radius = random(1.0f, 2.0f);
x = entryX + cos(angle) * radius;
y = entryY + sin(angle) * radius;
groundZ = map->GetHeight(x, y, entryZ + 2.0f, true, 5.0f);
z = groundZ有效 ? groundZ : entryZ;
orientation = atan2(bossY - y, bossX - x);
```

每个候选落点都必须执行地图坐标、碰撞、高度、可行走和与Boss距离检查。找不到合法散点时，只能在同一传入点附近使用经过校验的备用偏移，不得把玩家发送到未配置的默认入口。

## 5. 两张静态配置表

数据库只保存Boss静态配置，不保存实例运行态。

### 5.1 配置表1：`heroic_dungeon_rift_boss`

一行代表一个可进入随机池的Boss基础配置。

| 字段 | 类型 | 说明 |
|---|---|---|
| `boss_id` | `INT UNSIGNED` | 自定义Boss ID，主键；用于C++ Boss逻辑分派 |
| `map_name` | `VARCHAR(64)` | 副本名称，供管理界面和日志显示 |
| `map_id` | `SMALLINT UNSIGNED` | AzerothCore副本地图ID |
| `player_entry_x` | `FLOAT` | 默认玩家传入点X |
| `player_entry_y` | `FLOAT` | 默认玩家传入点Y |
| `player_entry_z` | `FLOAT` | 默认玩家传入点Z |
| `player_entry_o` | `FLOAT` | 默认玩家传入朝向 |
| `enabled` | `TINYINT UNSIGNED` | 是否进入随机池 |
| `remark` | `VARCHAR(255)` | 坐标来源、Boss备注和维护说明 |

`boss_id`是自定义配置ID，不等同于核心的 `creature_template.entry`。

### 5.2 配置表2：`heroic_dungeon_rift_boss_tier`

一行代表一个Boss在一个Tier下的最终运行参数。每个Boss通常配置T1、T2、T3三行。

| 字段 | 类型 | 说明 |
|---|---|---|
| `boss_id` | `INT UNSIGNED` | 关联配置表1 |
| `entry_id` | `INT UNSIGNED` | 新的 `creature_template.entry`；Boss使用100001–100048 |
| `boss_spawn_x/y/z/o` | `FLOAT` | 现有副本Boss生成点 |
| `tier` | `TINYINT UNSIGNED` | 1、2、3 |
| `health_multiplier` | `DECIMAL(8,4)` | 血量倍率 |
| `damage_multiplier` | `DECIMAL(8,4)` | 伤害倍率 |
| `player_entry_x/y/z/o` | `FLOAT` | 该Tier最终使用的玩家传入点；通常复制表1，允许特殊Tier覆盖 |

主键为 `boss_id + tier`，`entry_id`必须唯一。

表1的传入点是Boss基础默认值，表2保存Tier最终生效值。运行时优先读取表2；如果表2传入点未填写或校验失败，则该Tier配置无效，不使用任意默认坐标。

### 5.3 配置加载

服务器启动时读取两张表，加载到内存配置缓存：

```text
BossConfig[boss_id]
TierConfig[boss_id][tier]
```

运行期间不应每次进入都依赖临时查询来拼接配置。配置加载失败、Boss缺少某个Tier或Entry不存在时，应在启动日志中报告并将该Boss-Tier排除出随机池。

## 6. 同一Boss只使用一个C++脚本

这是最终版本的关键约束。

### 6.1 脚本绑定规则

同一个Boss的T1、T2、T3虽然使用三个不同的 `entry_id`，但全部绑定同一个该Boss脚本。例如：

```text
死亡矿井范克里夫：
100001 / 100002 / 100003
ScriptName = boss_rift_vancleef

斯尼德：
100004 / 100005 / 100006
ScriptName = boss_rift_sneed
```

不创建以下形式的重复脚本：

```text
boss_rift_vancleef_t1
boss_rift_vancleef_t2
boss_rift_vancleef_t3
```

也不要求所有不同Boss共用一个万能Boss脚本。脚本粒度是“一个Boss一份脚本，三个Tier共用”。

### 6.2 脚本内Tier控制

每个Boss脚本在AI初始化或Boss召唤绑定阶段读取本场内存运行上下文：

```cpp
struct HeroicDungeonRiftTierConfig
{
    uint32 EntryId;
    uint8 Tier;
    float HealthMultiplier;
    float DamageMultiplier;
    Position BossSpawn;
    Position PlayerEntry;
};
```

Boss脚本通过统一的Tier值控制：

```cpp
switch (_riftTier)
{
    case 1:
        ConfigureTier1();
        break;
    case 2:
        ConfigureTier2();
        break;
    case 3:
        ConfigureTier3();
        break;
}
```

实际实现中可以共用同一组事件、计时器和技能函数，只在Tier判断中改变参数：

- `health_multiplier`：初始化Boss生命；
- `damage_multiplier`：普通攻击和技能伤害修正；
- Tier 2：在T1技能基础上启用额外技能或阶段事件；
- Tier 3：在T2技能基础上继续启用更高阶技能、缩短冷却或提高技能组合密度；
- 技能目标数量、技能伤害、触发阈值和技能冷却均由脚本内的Tier分支控制；
- 不根据队伍人数或NPCBot数量进行二次缩放。

技能增强通过C++运行时逻辑、`CustomSpellValues`、`SpellScript`或脚本伤害修正实现，不修改 `Spell.dbc`。

### 6.3 80级10人本伤害基线

首批裂隙Boss固定使用83级和WotLK属性列：

```text
minlevel/maxlevel = 83/83
exp               = 2
DamageModifier    = 35.0
```

83级提供标准团队Boss的415点近战/防御技能；`DamageModifier=35`取当前数据库中纳克萨玛斯等早期80级10人Boss的常见近战基线。现有表2 `damage_multiplier`继续在Boss最终造成伤害时应用一次，因此等效近战强度约为：

```text
T1：35 × 1.0 = 35
T2：35 × 1.4 = 49
T3：35 × 2.0 = 70
```

等级从20提高到83也会同时改变 `creature_classlevelstats`中的基础生命。**T1 血量基线按目标值正向设置**，使 83 级模板基础生命统一为 180 万，再由表2 `health_multiplier` 得到 T1/T2/T3 最终生命：

```text
T1 目标生命 = 1,800,000
83级模板 HealthModifier = 1,800,000 ÷ basehp2(83, 对应 unit_class)
   （战士类 basehp2=13945 → HealthModifier≈129.1；不同职业按各自 basehp2 折算，最终生命均为 180 万）

T1 = 180万 × 1.0 = 180万
T2 = 180万 × 1.8 = 324万
T3 = 180万 × 3.5 = 630万
```

`DamageModifier=35`取纳克萨玛斯 10 人全量 18 个 Boss 的一致近战基线，T1=35、T2=49、T3=70。生命与伤害基线均按固定值正向设置，不随源 Boss 低级属性变化；不再使用“反向折算保持源生命”的旧公式。

召唤物血量按比例设置：以原版召唤物与原版 Boss 的血量比例，乘以新 Boss 当前生命（180 万 × Tier 倍率）得到召唤物血量，保持原版的相对强度。82 级召唤物模板 `HealthModifier` 公式：

```text
召唤物 HealthModifier = 1,800,000
  × (源召唤物原始生命 ÷ 源 Boss 原始生命)
  ÷ basehp2(82, 对应 unit_class)
```

其中源召唤物/源 Boss 原始生命由 `creature_classlevelstats.basehp` × `HealthModifier` 求得，源 Boss 通过 `_rift_summon_map.boss_source_entry` 关联。运行期 `ApplySummonTierStats` 再按 Tier 与每召唤物系数做最终缩放。

原技能按实际伤害类型处理：

| Boss | 技能 | 伤害处理 |
|---|---|---|
| 范克里夫 | `3391` Thrash | 无独立伤害基础点，追加2次普通攻击；完全依赖83级近战基线与Tier最终倍率 |
| 范克里夫 | `16856` Mortal Strike | 200%武器伤害；依赖83级近战基线与Tier最终倍率 |
| 范克里夫 | `15589` Whirlwind | 武器伤害外加固定伤害；效果0局部覆盖为2500，再由Tier最终倍率应用一次 |
| 斯尼德 | `7399` Terrify | 只造成恐惧，不改伤害点 |
| 斯尼德 | `3603` Distracting Pain | 只降低施法速度，不改伤害点 |
| 斯尼德 | `15588` Thunderclap | 效果0局部覆盖为2500，再由Tier最终倍率应用一次 |
| 斯尼德 | `10101` Knock Away | 武器伤害外加固定伤害并击退；效果0局部覆盖为2000，再由Tier最终倍率应用一次 |
| 曲奇 | `5174` Cookie's Cooking | 自我治疗，不改伤害点 |
| 曲奇 | `6306` Acid Splash | 每5秒自然伤害，效果0局部覆盖为每跳2000，再由Tier最终倍率应用一次 |
| 曲奇 | `29901` Acidic Fang | 周期自然伤害兼有武器伤害和破甲；效果0局部覆盖为每跳1000，再由Tier最终倍率应用一次 |
| 曲奇 | `23861` Poison Cloud | 每秒周期自然伤害，效果0局部覆盖为每跳1500，再由Tier最终倍率应用一次 |

上述判断已用用户提供的 `outputs/Spell_dbc.csv`复核：`6306`振幅5000毫秒，`29901`振幅2000毫秒且最多叠加7层，`23861`振幅1000毫秒；`3391`确为额外2次攻击机会，`16856`为200%武器伤害，`7399/3603`均无直接伤害效果。由于周期持续时间仍由 `DurationIndex`间接引用，最终持续秒数和叠层压力仍需进服实测。

固定或周期伤害使用 `CastCustomSpell(..., SPELLVALUE_BASE_POINT0, ...)`，只覆盖本裂隙Boss当前这次施法，不修改全服 `Spell.dbc`，也不影响其他使用相同法术ID的生物。`DamageDealt`阶段再统一应用一次Tier倍率，禁止把Tier倍率预乘进上述C++基础点。

### 6.4 新增技能施法时间与免疫打断规则

T2/T3 新增技能按施法时间分档处理：

- **施法时间 > 1.5 秒的新增技能一律改为顺发**，用 `triggered=true` 实现（跳过读条）。
- **施法时间 ≤ 1.5 秒的新增技能保留读条，并免疫打断**：通过 `BossAIBase` 的 `AddInterruptImmuneSpell()` 注册技能 ID，`OnSpellStart` 读条开始时施加 `SPELL_EFFECT_INTERRUPT_CAST` 免疫、`OnSpellCast` 读条结束时解除，使 Kick/拳击/法术反制等打断对该读条无效。
- **原 Boss 技能（T1 基础技能）不改变**，保持与源 Boss 一致（包括读条与可打断性），不做全局免疫打断。

当前落位：恐惧 `12096`（1.5s）、纠缠根须 `12747`（1.5s）保留读条并免疫打断；其余新增读条技能（闪电箭/毒液喷吐/荆棘诅咒/冰冻术/烈焰风暴/暗影箭/支配心灵等，均 >1.5s）一律顺发。

**以后新设计的 Boss**：新增技能尽量选用瞬发技能；若没有合适的瞬发技能，则选用施法时间 **≤ 1 秒** 的技能。施法时间由脚本 `triggered=true/false` 控制，不通过 `spell_dbc` 覆盖、不修改 `Spell.dbc`。

void AddHeroicDungeonRiftScripts();

## 7. 分Tier模型、统一逻辑的出口传送门

### 7.1 GameObject模板

T1/T2/T3使用三个连续的出口模板，但共用同一个脚本：

```text
T1：gameobject_entry = 100500，displayId = 7148
T2：gameobject_entry = 100501，displayId = 8196
T3：gameobject_entry = 100502，displayId = 8197
三者：ScriptName = rift_exit_portal
```

当前核心的 `GameObject::SetDisplayId()`确实支持在对象已经进入世界后更换模型，并同步重建客户端字段和服务器动态碰撞模型。但统一Entry运行时换模仍有两个边界：

- `SummonGameObject()`先按模板默认模型创建，再调用 `SetDisplayId()`，附近客户端可能短暂收到默认模型后再更新；
- 部分服务器交互距离和边界计算仍读取 `GetGOInfo()->displayId`，即模板原始模型，而不是运行时模型。

因此最终采用三个模板Entry，使对象创建包、VMAP碰撞和交互边界从生成时起完全一致；不需要修改核心，也不直接写 `GAMEOBJECT_DISPLAYID` 更新字段。

### 7.2 动态生成

实例创建完成、玩家传入点校验通过并完成传送后，在该场实际生效的玩家传入点附近按Tier生成一扇动态出口门：

- 所有副本共用100500/100501/100502这组三档出口模板；
- 当前场次只根据Tier选择其中一个Entry；
- 三个Entry共用同一个 `rift_exit_portal` 对话和离场脚本；
- 每场只生成一扇门，不为每名玩家生成独立门；
- 门GUID、实例ID、Boss ID、Tier和 `runToken` 只保存在内存运行组件；
- 实例卸载、运行结束、超时或回滚时删除动态门。

### 7.3 固定对话与服务器控制

门的对话固定为：

```text
离开...
```

`GameObjectScript`在点击时校验：

1. 玩家当前地图和实例是否属于本场；
2. 玩家是否是本场已进入的真实玩家；
3. 门GUID和 `runToken` 是否有效；
4. 玩家是否已经离场；
5. 是否存在本场共享返回点。

校验通过后，服务器读取本场唯一的共享返回点。这个返回点只在入口对话者发起挑战时记录一次：

```text
入口对话者进入前的地图
入口对话者进入前的实例ID（如果原位置属于实例）
入口对话者进入前的X/Y/Z/O
```

无论是入口对话者、队长还是其他真实队员，只要通过本场出口门选择“离开...”，都传送到上述同一个位置。成员传送成功后只标记该成员已经离场，不删除共享返回点；共享返回点保留到全体成员离开或本场运行上下文清理。客户端不能提交或修改返回坐标。

## 9. 实例创建、传入和清理

### 9.1 创建顺序

```text
队长选择T1/T2/T3
    ↓
检查队伍、队长权限和最多5席位
    ↓
只保存入口对话者的共享返回位置
    ↓
随机Boss并读取Tier配置
    ↓
创建对应普通InstanceMap并确认instanceId
    ↓
全体真实玩家预绑定到同一个InstanceSave
    ↓
全体真实玩家进入同一实例
    ↓
在传入点1至2码范围安全散点
    ↓
生成对应Tier Boss
    ↓
按Tier生成对应模型的出口门
    ↓
Boss进入可战斗状态
```

Boss必须使用表2的 `entry_id` 和 `boss_spawn_x/y/z/o`。不使用源Boss的静态世界刷怪，不把T1/T2/T3作为客户端地下城难度分支。

### 9.2 失败回滚

- 随机配置无效：不创建运行态，不传送玩家；
- 队长入本失败：使用入口对话者的共享返回点回滚；
- 队员入本失败：失败成员和需要整体回滚的其他成员均返回同一个共享返回点；推荐本场整体回滚；
- Boss生成失败：删除动态门，所有已传入真实玩家返回入口对话者的共享返回点；
- 运行上下文失效：门不可用并删除，不能继续接受客户端请求。

### 9.3 死亡、释放灵魂和实例销毁

核心判断实例内是否有玩家使用 `Map::HavePlayers()`，本质上检查地图玩家引用容器是否为空，不检查玩家是否存活。因此：

1. 玩家死亡但尚未释放灵魂时，玩家对象仍在实例地图中，实例仍被视为有人，不会启动空图卸载；
2. 玩家释放灵魂后，核心通常把幽灵送到副本外墓地；当最后一名玩家对象离开实例后，`InstanceMap::AfterPlayerUnlinkFromMap()`启动空实例卸载计时；
3. 默认 `Instance.UnloadDelay=1800000`，即30分钟，实例不会在全员释放后立即销毁；
4. 玩家在30分钟内跑尸并重新进入时，临时 `InstanceSave`绑定仍指向原 `instanceId`，进入同一实例，同时 `InstanceMap::AddPlayerToMap()`将卸载计时清零；
5. 若30分钟内无人重新进入，核心在计时结束后调用实例销毁流程；裂隙的 `OnDestroyInstance`回调随后清理Boss、出口门、内存运行态和仍指向该实例的临时玩家绑定；
6. 实例地图对象销毁与 `InstanceSave`删除是两个概念。地图对象先卸载；当没有玩家绑定且地图已不存在时，`InstanceSave`才满足删除条件。

`MemberState::Exited`只表示永久离场。仅以下路径可以设置为真：

- 玩家通过裂隙出口门成功传回共享位置；
- 启动失败或运行失败时，玩家成功回滚到共享位置；
- 裂隙超时回滚完成。

普通地图离开事件不再设置 `Exited=true`，因此释放灵魂、断线或临时离图不会提前触发“全员已经离场”的脚本清理，也不会提前解除跑尸所需的临时绑定。

核心30分钟空图计时与裂隙2小时运行超时的关系是“先到者生效”：

- 全员释放且30分钟无人返回：核心先销毁空实例并触发裂隙清理；
- 实例中一直有人或期间有人返回：核心不销毁，裂隙最多保留至2小时运行超时；
- 2小时先到：裂隙执行回滚和清理，不再继续保留本场。

### 9.4 重复挑战

裂隙玩法本身不设置日锁、周锁、Boss锁定、次数或额外冷却，允许队伍连续反复挑战。

服务器核心的 `AccountInstancesPerHour` 计划调整为50，作为核心滚动小时安全上限。该上限不是裂隙自身的日/周限制。每场结束后必须：

- 让成员安全离开实例；
- 清理本场运行上下文；
- 删除出口门；
- 解除临时实例绑定；
- 下一场创建新的 `instanceId`。

## 10. 数据库与SQL交付边界

Entry按以下互不重叠的区间分配：

```text
入口NPC：100000
16个Boss的T1/T2/T3模板：100001–100048
裂隙专用同伴和召唤物：100100–100110
T1/T2/T3出口门：100500–100502
```

Boss编号从1开始时，其三个Tier连续分配：

```text
T1 = 100001 + (boss_id - 1) * 3
T2 = T1 + 1
T3 = T1 + 2
```

三档Entry复制源Boss的必要模板数据：

- `creature_template`基础属性；
- `creature_template_model`模型；
- `creature_template_spell`基础技能；
- `creature_template_resistance`抗性；
- 必要的 `creature_template_addon`。

覆盖字段：

- `entry`改为新Entry；
- `difficulty_entry_1/2/3`置0；
- `minlevel/maxlevel=83/83`、`exp=2`，获得标准80级团队Boss的属性和415点近战技能；
- `DamageModifier=35.0`作为早期80级10人本近战基线，表2伤害倍率只由C++在运行时应用；
- `HealthModifier`按目标值正向设置：`1,800,000 ÷ basehp2(83, 对应 unit_class)`，使 83 级模板基础生命统一为 180 万（T1 基线）；表2生命倍率（1.0/1.8/3.5）只由C++应用；
- `ScriptName`设置为该Boss唯一脚本名，例如 `boss_rift_vancleef`；
- Boss通常清除不适用的NPC标志和巡逻路径；
- T1/T2/T3如需独立掉落，后续分别配置对应掉落Entry。

不使用 `INSERT ... SELECT *`，应使用显式列名，防止核心字段变化导致错位。SQL只生成并审核，不自动执行。

当前唯一应审核的整合SQL文件：

```text

```

早期的死亡矿井首批SQL和简化配置SQL均已废弃，不得与整合SQL同时执行。

## 11. 明确不采用的方案

- 不为同一个Boss的T1/T2/T3分别创建三份C++脚本；
- 不让同一Boss的不同Tier使用不同 `ScriptName`；
- 不使用一个覆盖所有Boss的万能脚本代替“每个Boss一份、三个Tier共用”的脚本结构；
- 不按玩家或Bot数量动态调整Boss强度；
- 不伪装LFG队伍；
- 不把运行态写入数据库；
- 不使用全局Recall点作为共享返回位置；
- 不记录每个队员各自的离场返回点，只记录入口对话者的位置；
- 不为每个玩家生成一扇出口门；
- 不将共享返回坐标交给客户端控制；
- 不修改 `Spell.dbc`。
