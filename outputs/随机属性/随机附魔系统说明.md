# 装备掉落随机附魔系统说明

按「法系 / 物理 / 防御 / 治疗」四组，在装备掉落时随机附加一条属性（ItemRandomProperties）。

## 一、数据链路（自定义表方案）

本方案**不走**原版 `item_enchantment_template`（物品模板也不写数据库），由脚本在获得装备时动态判断分组并附魔：

```
拾取 / 制造 / 团队roll → 装备等级 > 220 且 roll 概率命中 → 脚本按主属性推断分组
        ↓ 两级 roll：先等概率选属性，再在属性内按装等动态权重选组合
mod_random_enchant（自定义表：entry=分组, ench=组合ID, attr=属性名, attr_type=ItemModType, tier=档位序号, chance=低装等基准权重）
        ↓ ench = ItemRandomProperties.dbc 的 ID（每个组合 = 单条属性）
ItemRandomProperties.dbc（组合，Enchant[0] = 基础附魔 ID）
        ↓ Enchant = SpellItemEnchantment.dbc 的 ID（type=5 STAT）
SpellItemEnchantment.dbc（EffectArg=属性ID，EffectPointsMin=数值）
```

### 随机属性标记组（装备链接能不能发出去的关键）

装备链接能不能发出去，取决于**服务端**的链接校验（不是客户端）：

- 玩家发聊天消息时，`WorldSession::HandleMessagechatOpcode` 会调用
  `ValidateHyperlinksAndMaybeKick` → `Acore::Hyperlinks::CheckAllLinks` 校验消息里的所有链接；
- `Acore::Hyperlinks::LinkTags::item::StoreTo`（`src/server/game/Chat/HyperlinkTags.cpp`）**原版**要求：
  「链接中 `randomPropertyId > 0` 时，物品模板的 `item_template.RandomProperty` 必须非 0」
  （后缀方向同理要求 `RandomSuffix` 非 0）；不满足即判整条链接非法；
- 校验失败 → `ChatHandler.cpp:352` 直接 `return` → **整条聊天消息被静默丢弃**
  （日志会打 `Player xxx sent a message with an invalid link:`，`ChatStrictLinkChecking.Kick = 1` 时还会踢人）。

原版数据里正向 `RandomProperty` 只用在 ≤70 级的旧世界物品上（装等 >220 的物品**一件都没有**），
本方案的随机属性只挂在**物品实例**上、模板 `RandomProperty = 0` → 于是链接被判非法、消息发不出去
（这才是"随机附魔装备链接发不出去"的真正原因；客户端显示一直是正常的）。

**做法：去掉核心里的这条限制**（模块自身不做任何内存/数据改动）

| 文件 | 改动 |
|---|---|
| `src/server/game/Chat/HyperlinkTags.cpp` | `LinkTags::item::StoreTo` 中删除 `if (!val.Item->RandomProperty) return false;` 与 `if (!val.Item->RandomSuffix) return false;` |

去掉后，链接仍然要求 **`ItemRandomProperties.dbc` / `ItemRandomSuffix.dbc` 里存在对应条目**
（以及后缀的 `suffixFactor` 一致性），也就是说"能凭证的随机属性 ID"仍然会被校验，
只是不再要求"物品模板必须自带同类随机属性"。这样：

- 随机附魔（本方案，实例正向属性 + 模板 0）链接可正常发出；
- 「属性萃取/转移」把后缀注入到模板无 `RandomSuffix` 的装备上时，链接同样正常（原版也会被拒）；
- 物品模板数据库与内存都不需要任何改动，`enchant_template_group.sql` 之类的方案已废弃删除。

**部署顺序与运维注意**

1. 只需**重新编译 + 重启**（核心补丁），无需任何 SQL / DBC 调整；
2. 若玩家仍发不出链接，先看服务端日志里的 `sent a message with an invalid link`：
   有这行说明随机属性 ID 在**服务端 `dbc/`** 里查不到（没导入 10000～11306 段），
   或链接里还带着其它非法字段；
3. `ChatStrictLinkChecking.Kick` 建议保持 0（默认），避免排查期间玩家被踢。

### 名称格式

| DBC | 字段 | 取值 | 说明 |
|-----|------|------|------|
| `ItemRandomProperties.dbc` | `Name`、`Name_Lang_deDE`、`Name_Lang_zhCN` | `法·` / `愈·` / `攻·` / `防·` | 分组前缀，显示在装备名旁（如「法·迅捷之刃」）；**不能带颜色码**，否则 `\|` 会破坏物品链接 |
| `SpellItemEnchantment.dbc` | `Name_Lang_deDE`、`Name_Lang_zhCN` | `\|cff0070dd+10 力量\|r` | 附魔描述名（附魔窗口等展示），保留蓝色品质色 |

> 两张 DBC 的名称都同时写入 `deDE` 与 `zhCN` 两列：服务端按 `DBC.Locale` 取列，
> 客户端按自身语言取列，两列都写可避免客户端取到空名称（空名称会导致装备名/物品链接异常）。

## 五、部署步骤

1. **生成数据**（已执行）：`python 生成随机附魔数据.py`
2. **导入 DBC**：用 WDBX 把两个 CSV 分别导入 `SpellItemEnchantment.dbc` 和 `ItemRandomProperties.dbc`。
   - **服务端 `dbc` 目录必须更新**：`Item::SetItemRandomProperties` 靠 `sItemRandomPropertiesStore` 才能设上属性，
     链接校验也靠它按 ID 取名字；
   - 客户端补丁建议同步更新（装备名/属性行靠客户端的同一份 DBC 显示；DBC 与服务端不一致时玩家看到的属性行会缺失）；
   - `SpellItemEnchantment.dbc.csv` 字段名与既有混沌宝石脚本一致，可直接导入；
   - `ItemRandomProperties.dbc.csv` 的字段名是 WDBX 标准命名，导入前**先用 WDBX 导出现有 `ItemRandomProperties.dbc` 的表头核对列名**（尤其内部名字段 `Name`），必要时按实际表头调整 `PROP_CSV_FIELDS`；
   - 中文文本统一写入 `Name_Lang_deDE` 列，并**同时补写 `Name_Lang_zhCN` 列**（保险，见「名称格式」）。
3. **执行 SQL**：把 `modules/mod-random-enchants/sql/world/custom_random_enchant.sql` 执行到 `acore_world`（幂等）。
4. **重新编译** worldserver（含 `HyperlinkTags.cpp` 那处核心补丁；模块由 `RE_loader.cpp` 的 `Addmod_random_enchantsScripts()` 注册）。

### 装备链接发不出去时怎么查

链接是否合法由**服务端**判定（`ValidateHyperlinksAndMaybeKick` → `CheckAllLinks` → `LinkTags::item::StoreTo`），
排查顺序：

1. **服务端日志搜 `sent a message with an invalid link`** —— 有这行说明链接被判非法了；
2. 服务端 `dbc/ItemRandomProperties.dbc` 里是否存在物品随机属性 ID（**10000～11306**）——
   缺了会走到 `StoreTo` 的 `LookupEntry` 失败分支（判非法）；`dbc/` 与客户端补丁不一致时客户端也看不到属性行；
3. 确认 `HyperlinkTags.cpp` 的这处补丁已编译进去（`StoreTo` 里不应再有 `if (!val.Item->RandomProperty)` /
   `if (!val.Item->RandomSuffix)`）；
4. 若配置了 `ChatStrictLinkChecking.Kick = 1`，玩家会被直接踢下线，建议先设为 0 便于排查。

## 六、分组判断规则（脚本内，可调）

脚本按装备主属性推断分组，优先级从高到低：

1. **防御**：有防御等级/躲闪/招架/格挡等级、格挡值；
2. **物理**：有力量/敏捷/攻击强度——**即使同时带智力也算物理**（猎人、增强萨锁甲）；
3. **法系/治疗**（有智力/法伤）：
   - 有每5秒回蓝 → 治疗；
   - 有法术命中/穿透 → 法系；
   - 有精神 → 治疗；
   - 其余 → 法系；
4. 无法归类（如无属性白字武器）→ 不附魔。

盾牌按自身属性判定（不再无条件算防御）：带防御评级 → 防御，法伤+回蓝/精神 → 治疗，
法伤+命中/穿透 → 法系。

> 可附魔部位由 `RandomEnchantCommon.h` 的 `IsEquipmentSlot()` 决定，与「属性萃取/转移」
> 共用同一份判定：覆盖全部装备槽（含戒指/饰品/圣物），排除包、弹药、箭袋、衬衫、战袍。

分组确定后，脚本执行**两级随机**：

1. **选属性**：从该分组内的属性集合中**等概率**随机选一个属性；
2. **选条目**：在该属性的所有档位中按**装等动态权重**随机选一条。权重随装备等级线性过渡：
   - 低装等（≤ `WeightMinLevel`）：低数值档位权重最大（`权重 = chance = 档位数 - tier + 1`）；
   - 高装等（≥ `WeightMaxLevel`）：高数值档位权重最大（`权重 = tier`）；
   - 中间装等：在两者之间线性插值，越高的装等越偏向高数值档位。

## 七、关键前提与可调参数

- **触发时机**：与 `RandomEnchantsScript.cpp` 一致——**拾取**（`RandomEnchants.OnLoot`）、
  **制造**（`RandomEnchants.OnCreate`）、**团队 roll**（`RandomEnchants.OnGroupRoll`）三个开关；
  任务奖励 / 商人购买 / 邮箱 / 交易**不触发**。
- **触发条件**：仅装备等级 **> 220**（`RandomEnchants.Custom.MinItemLevel`）且 roll 概率命中（`RandomEnchants.Custom.Chance`）才附魔，两者均可配置。
- **配置读取**：所有配置在启动 / `.reload config` 时一次性读入内存缓存（`RandomEnchants` 相关），
  事件触发时不再查配置。
- **与模块内原脚本不冲突**：原有 `RandomEnchantsScript.cpp` 附魔在永久附魔槽（`PERM_ENCHANTMENT_SLOT`，槽 0），本脚本附魔在随机属性槽（`PROP_ENCHANTMENT_SLOT_0` 起，槽 7~11），槽位不同、互不覆盖，无需 entry 隔离。
- **不覆盖原生随机属性**：装备的 `item_template.RandomProperty` / `RandomSuffix` 必须为 0，否则核心会用原生随机属性覆盖脚本设置。
- **属性/数值/步长/分组**：在 `生成随机附魔数据.py` 的 `ATTRIBUTES`（属性清单）、`GROUP_DEFS`（分组）里改，重新运行脚本即可重生成。

### 配置项（`RandomEnchants.conf.dist`）

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `RandomEnchants.Custom.Enable` | 1 | 是否启用四分组方案 |
| `RandomEnchants.Custom.Chance` | 100.0 | 装备等级达标后，触发附魔的概率（%） |
| `RandomEnchants.Custom.MinItemLevel` | 220 | 触发附魔的最低装备等级（严格大于） |
| `RandomEnchants.Custom.WeightMinLevel` | 220 | 权重偏好下限（≤ 该值低数值权重最大） |
| `RandomEnchants.Custom.WeightMaxLevel` | 284 | 权重偏好上限（≥ 该值高数值权重最大） |
